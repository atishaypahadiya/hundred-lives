## Running

```bash
uv sync
OLLAMA_CONTEXT_LENGTH=16384 ollama serve &
uv run python -m orchestrator.sandbox up       # once: Gitea on 127.0.0.1:3000, agent image, admin user
uv run python -m orchestrator.sandbox check    # isolation probes from a throwaway agent container
uv run python -m orchestrator.run --persona agents/personas/maya.yaml --runs 10   # 52 weeks each
uv run python analysis/summarize.py runs/maya-*.jsonl
uv run python -m viewer.server                  # http://127.0.0.1:8711, read-only on runs/ (--runs-dir repeatable)
uv run python -m viewer.export <run_id> --deny real-names.txt   # docs/replays/<run_id>/ + scrub-report.json
```

- `viewer.export` (Phase 3) writes a self-contained replay: the page with the run's normalized events, summary and repo summaries embedded as JSON (no server, no fetches, no Google Fonts; opens from `file://`). It scrubs what it publishes: home paths → `~`, emails → `[email removed]`, and any secret-looking string, secret-named field, or `--deny` name (a local list of real people, never committed) refuses the export with nothing written. It lists the persona's contacts in `scrub-report.json` for a person to confirm they're fictional.
- The viewer never writes under `runs/` and renders every logged string as text, never HTML (agent-made content). It reads logs only, so anything it shows must be in the log. `idea` events are derived for now (reflections, files the agent wrote, launch pitches); thinking blocks aren't logged yet. Quiet git (`commit -q`, `push -q`) is read from the command text and labelled as such.

- `--agent-model ollama:<model>` (default `ollama:qwen3:8b`; `--model` is an alias) or `claude-*` / `anthropic:<model>`. `--referee-model` and `--summary-model` default to the agent model. Both are logged in `run_start` and `run_end`, and every `llm_call` logs its model. For showcase runs keep the referee fixed at `claude-haiku-5-5` even when the agent model changes.
- `--sandbox docker` (default) needs `orchestrator.sandbox up` and OrbStack running; `--sandbox none` drops `shell`/`launch` and the code host (the v0.2 world).
- `--runs > 1` refuses to start with uncommitted changes under `orchestrator/ world/ agents/ sandbox/` unless `--allow-dirty`. `run_start.code` records the commit and a dirty flag; the summarizer labels dirty or unrecorded runs as PILOT. `--world` defaults to `world/openings.yaml`. `--seed` (default 0) is the base seed; run *i* uses `seed + i` for both the opening order and the outcome dice, through separate RNGs. `--order-seed N` / `--dice-seed N` fix one of them to N for every run in the batch (`run_start.order_seed`, `dice_seed`). Runs from before the split have only `seed`, which was both.
- **Models:** qwen3:8b is for plumbing only (does the loop, the sandbox, the logging work?). Real experiments use Haiku (`claude-haiku-5-5`) as agent, referee, and summarizer; the referee stays fixed at Haiku even if the agent model changes.
- Each batch first scores a fixed average-applicant submission (`referee.BASELINE_PERSON`, `BASELINE_DETAILS`) against every opening and logs it to `runs/<batch>-referee-baseline.jsonl` (`referee_baseline` per opening, `referee_baseline_summary`). A calibrated referee gives about the base rate; report estimate / base. `--skip-referee-baseline` skips it.
- The world and persona files are read once per batch; `run_start.sources` has their full text and sha256, so editing `world/` mid-batch doesn't change a running batch, and every run records exactly what it used.
- `--label exp01a` puts a tag in every run id (`maya-exp01a-<stamp>-001`), so batches started in parallel can't collide and an experiment's runs are easy to select.
- `--max-tokens` is the **per-run token budget** (every call's input + output + cache tokens, including referee and summary calls), not a per-response limit. Before each call the run checks a conservative estimate (prompt chars / 3 + max output) against what's left and ends with `run_end.reason = "token_budget"` instead of overshooting.
- `--horizon` (default 52) is the number of weeks; the persona's `horizon` (260 for Maya) is the cap, so `--horizon 260` runs the full five years. `--max-tokens` defaults to 1.5M, about twice what a 52-week qwen3:8b run uses.
- Ollama's default context is small and truncates silently, so always start it with `OLLAMA_CONTEXT_LENGTH=16384`. `OLLAMA_BASE_URL` overrides `http://localhost:11434/v1`.
- Anthropic needs `ANTHROPIC_API_KEY` in `.env` (or an `ant auth login` profile). Ollama runs are free; Anthropic runs cost money, so ask before launching them.
- Cost: every `llm_call` logs `cost_usd`, computed from the API's usage fields (`input_tokens` excludes cache reads/writes, which are priced separately) with `backends.PRICES` for the model that actually served the call, plus `raw_usage` verbatim. Haiku 5.5 cache prices in `PRICES` are an assumption until a run's total is reconciled with the Console usage page.

## How a week works

1. Commitments past their `ends_week` end. Held offers start if they now fit, or lapse after `OFFER_HOLD_WEEKS`. Pending decisions whose `reveal_week` has come are applied and shown as news. Then the week's action budget is fixed: `ACTIONS_PER_WEEK` (8) minus the time commitments use.
2. If cash + income < expenses, the agent is **broke**: a `broke` event is logged, `wait` is refused until it takes a gig or applies to a `job` opening, and if the week ends without one a gig is forced (`gig.forced = true`). Cash is floored at $0; any uncovered amount is logged as `week_end.shortfall`.
3. The agent gets a **fresh conversation**: the fixed system prompt (persona + rules + openings catalog in this run's shuffled order, cached) plus a week prompt rendered from state, memory, and last week's unseen errors. Earlier weeks are never replayed as raw messages, so no thinking blocks are ever edited or dropped.
4. **Time budget.** Valid `files`/`shell`/`apply`/`launch`/`message`/`spend`/`leave` calls use 1 action, a gig uses `gig.time_cost` (5, for $1,200), and `wait` is free. A full-time commitment uses `time_costs.full_time` (5) every week, part-time 3, and commitments can't total more than 8. An accepted offer that doesn't fit is held for 2 weeks (the agent can `leave` something to make room). **Invalid calls use no actions**, but after `MAX_INVALID_PER_WEEK` (3) the week ends (`week_end.reason = "invalid_calls"`). A hired contractor adds coding actions (usable only for `shell`/`files`, spent before the general ones). When all actions are used, the agent gets one closing turn (`closing_turn`) to call `wait`; the week then ends (`week_end.reason = "wait"`, `closing_turn = true`, or `"out_of_actions"` if it didn't). The week also ends at `wait` or after a text-only reply plus one nudge. Calls after the week ended are reported next week.
5. `apply(opening_id, details, attachments)` → the referee sees the opening, its `base_rate`, the submission, and the attached workspace files. It returns `estimated_chance`, `decision_in_weeks`, `message_if_success`, `message_if_failure`, `rationale`; **it never picks the outcome**. `referee.draw` samples it with keyed dice: success if `u < estimated_chance`, otherwise failure if `v < reply_rate` (per opening), else ignored. **Dice are common random numbers** (`referee.uniform`, `run_start.dice_scheme = "keyed-sha256-v1"`): each draw is sha256 of its key, `[dice_seed, "apply" | "reply", opening_id, n]` for the n-th application to that opening, or `[dice_seed, "launch" | "launch_upvotes", repo, n]`. It never depends on what else the run did, so two runs with the same dice seed that make the same choice get the same draw whatever their paths. The seed, chance, draws and keys are in `referee_decision` and `launch`. Runs without `dice_scheme` used one sequential RNG, so their draws aren't comparable across paths. What a success *gives* (pay, stipend, grant, investment) is fixed by the opening, never by the referee. Ignored applications drop off the pending list after 6 weeks. An opening can be applied to again 26 weeks after the last application (`tools.REAPPLY_AFTER_WEEKS`, also stated in the apply tool's description); the pending list shows that week.
6. `message(contact_id, text)`: contacts are the persona's `contacts` (parents, three classmates, a former manager). The agent sees each one's name and relationship; `reply_rate`, `voice`, `known_as` and `offers` are hidden from it (`HIDDEN_FROM_AGENT`) and from the referee. Whether a message gets a reply is keyed dice `[dice_seed, "message", contact, n]`. A reply is written by the referee model in its own call (role `contact`) that sees only the contact's `voice`, the thread, and the offers they can still make. `referee.parse_contact` keeps an offer only if it's on that contact's list: a `referral` to a listed opening (once per opening; goes with the next application to it within `REFERRAL_VALID_WEEKS` = 26, and the reviewer sees "Referred by <known_as>") or a `paid_pilot` capped at `max_amount` (once; paid into company funds and added to the public track record). Dropped or capped offers are logged as `offer_problem`.
7. `spend(item)` uses company funds only (`company_funding` raised + `company_revenue` from pilots − `company_spent`; never personal cash, which can't be spent at all). Prices are in `world/openings.yaml` `spend`: `contractor` (per week, paid up front, starts next week, one at a time, adds `coding_actions`), `launch_ads` (the next launch of that repo within `valid_weeks` uses the ads' `traction_base_rate`, and the launch referee is told it was promoted). The referee's "money raised" is still `company_funding` only.
8. With a sandbox, new Gitea repos are logged (`repo_created`) and the workspace is copied to `runs/<id>/workspace/` within the sync caps.
9. Cash += income − expenses. **Memory facts are kept by code**: each week adds a `WeekRecord` (full digest plus key events: applications, replies, commitments starting or ending, offers). The agent sees the current quarter in full and older quarters condensed to key events plus gig and broke counts; cash, commitments, and open applications come from state. The LLM writes only a short "reflections and plans" note (≤120 words) every 13 weeks (`memory_reflection`). No LLM-written facts, so there's nothing to cite-check.

## The student world (`world/student.yaml`, persona `self.yaml`)

A second world for the "Self" persona: two years of a CS degree as an international student, then the months after. Every new mechanic switches on only when its key is in the world file, so Maya's prompts are byte-identical to before (checked by rendering every prompt on both commits).

- `calendar`: the referee's and contacts' "week 1 is …" text and the opening kinds named in the referee's system prompt.
- `academics`: semesters; classes are a commitment (`kind: "academics"`) of `class_actions` each semester week that `leave` refuses; `graduated` event at `graduation_week + 1`. The referee's person block gets a student-status line and follower count (`Run._status`), new worlds only.
- `work_authorization`: each opening's `auth` kind is allowed `always`, while `enrolled`, or once `graduated`, with an optional semester cap on actions (`world.auth_problem`). Applying to something not allowed is a tool error; the catalog marks it; a commitment that loses authorization ends (`commitment_ended.reason = "work_authorization"`). Illustrative F-1 rules, not legal advice.
- Openings may have `listed_weeks` (hidden outside, not counted as hidden), `start_week` (accepted → "coming up", becomes a held offer that week), `company_amount` (non-dilutive, to company funds).
- Hackathons (`type: hackathon`): decision before `event_week`; that week uses `attend_actions` and adds `build_actions` to the coding pool; `submit(opening_id, repo, pitch)` (free) is judged with `prize_base_rate` (`referee.JUDGE_SYSTEM`), dice `[dice_seed, "hackathon", id, 1]`; logs `hackathon_week`, `hackathon_result` (placed / not_placed / no_submission).
- `feed` + `post(text, repo?)`: the referee (role `audience`) estimates a breakout chance and writes candidate replies with made-up handles; code draws breakout, Pareto luck, likes, follows, replies, each on its own key (`referee.draw_post`). Logged as `post`; followers in every snapshot. With the file's numbers a new account's post gets 0–2 likes most of the time (p99 ≈ 20).
- Contacts in `self.yaml` are fictional. `address_as` (contact) and optional `address_note` (persona) say how to address the persona. Offer kinds beyond `referral`/`paid_pilot`: `money` (to personal cash, `max_amount`, once per semester via `world.term`, breaks counting with the semester before), `teammate` (listed `hackathons`, once each: +`TEAMMATE_BUILD_ACTIONS` in the event week and the judges see the team), `boost` (`reach`, `community`, once: added reach on the next post within `BOOST_VALID_WEEKS`). A persona with any of these gets `CONTACT_SYSTEM_EXTENDED` / `CONTACT_SCHEMA_EXTENDED`; others keep the originals byte for byte.
- `experience` is a public field (`PUBLIC_FIELDS`); Maya has none, so her referee prompts are unchanged.
- Sensitivity variants (`agents/personas/self-nosolo.yaml`, `self-socialgoal.yaml`, `self-goalonly.yaml`) carry `referee_view`: the base persona's public fields plus `network`, which the referee uses instead of the persona's own (hidden from the agent, `HIDDEN_FROM_AGENT`). So the referee sees the same person in every condition, and a changed trait reaches outcomes only through the agent's choices. Contacts are identical to `self.yaml`, so goal-only still meets De Anza and ISA friends through the contact list. Compare conditions with `analysis/self_lives.py name=glob ...`.
- `training` (world key) enables `train(activity)` (1 action, no effect on the world): logged as `train`; `train_streak` (weeks in a row with a session) is in the snapshot and the week prompt, and the viewer shows a streak tile. A week with no free actions holds the streak instead of resetting it (`train_streak_held`). `training.show_streak: false` (`world/student-hiddenstreak.yaml`, otherwise identical to `student.yaml`) keeps counting and logging the streak but never shows it: the `train` tool's description and result and the week prompt leave it out.
- Hours: with `time_costs.hours_per_action` (10.5 in the student world: ~84 usable waking hours / 8), a part-time opening may give `hours_weekly`; its cost is hours / hours_per_action rounded half up, at least 1 (`world.time_cost`), and the catalog says "About N hours a week". Student world: classes 3, a 10-hour campus job 1 (so a semester week with both leaves 4), full-time 4, gig 2 for $360, semester work capped at 2 actions (20 hours).
- In worlds with `academics`, the reflection prompt states the week ("It is the end of week N"); Maya's is unchanged.

## The live gateway (`gateway/`, Track B)

The Self persona in real time on X: `python -m gateway.run turn|dispatch|loop|status|publish|kill|unkill`. Built and tested offline; **nothing has been posted**.

- The agent only drafts (`draft_post`, `draft_reply`, `done`); drafts wait in the outbox until a person approves them on the viewer's `#/gateway` page. There is no code for DMs, follows, likes, reposts, or search.
- Rules are constants in `gateway/policy.py`, checked at draft time and again just before sending: ≤3 posts a day (UTC) including replies, ≤1 of them with a link, replies only to someone who engaged first and only mentioning them, no other mentions, ≤100 reads a day, and the profile bio must disclose an AI agent running a simulated life with the project link (checked live before any send).
- Dry run is the default (no request leaves the machine; fake ids). `--live` calls X; `--live-github` pushes approved mirrors. Dry and live state are separate: `gateway/state/{dry,live}/gateway.jsonl` (gitignored) is the only state, an append-only event log; `KILL` in that dir stops every turn and send.
- Inbound posts reach the agent inside `<untrusted>` blocks with control/bidi characters stripped and the closing tag neutralized.
- The GitHub publisher mirrors a run's exported bundle (never live Gitea), refuses any repo whose history has a secret-looking string or a real email, and creates the repo private in `GITHUB_ORG`. The token reaches git only as an env-config header.
- Credentials (`X_USER_ACCESS_TOKEN`, `X_USER_ID`, `GITHUB_TOKEN`, `GITHUB_ORG`, optional `X_COST_PER_*_USD`) live in `.env` only, never in prompts, logs, containers, or commits.
- The viewer's gateway endpoints are its only writes, and they go to the gateway state dir, never `runs/`; they need the `X-HL-Token` header (token in `gateway/state/approve.token`, 0600) and a loopback Origin.

## Sandbox

- The agent loop runs on the host. A container only runs `shell` commands and `files` reads/writes; it never sees the model endpoint, API keys, or the host filesystem.
- **Network:** every network is `internal: true`, Gitea's included, so nothing has a route out. Each run gets its own `hl-net-<run>` holding only its container and Gitea (alias `gitea`), so agents can't reach each other. The host reaches Gitea at its `hl-agents` IP (`sandbox.gitea_host_url`; OrbStack routes the Mac to internal networks). Don't use `hl-gitea.orb.local`: it resolves to a stale address once a run network is deleted. Gitea's app.ini also turns off migrations, mirrors, Actions, packages and Gravatar, and limits webhooks to loopback.
- **Tenancy:** one private Gitea user per run (repo-scoped token, 20 repos, every repo forced private, sign-in required to view anything). At run end its repos are exported to `runs/<id>/repos/<repo>.bundle` (`repos_exported`) and the user is purged (`gitea_user_deleted`), so each run starts from an empty code host.
- **Limits** (`sandbox.LIMITS`): 1 CPU, 1 GB memory (no swap), 256 pids, `--cap-drop ALL`, `no-new-privileges`, uid 1000, `--read-only`. Writable: the workspace (256 MB tmpfs, which is the disk quota), `/tmp` (64 MB, also `$HOME`), `/dev/shm` (16 MB; OrbStack's default is about 6 GB).
- **Processes:** each `shell` call is its own session: a 60 s timeout, and afterwards `reap()` kills every leftover process through PID 1 (`sandbox/init.py`, signalled with `docker kill --signal USR1`). That needs no exec, so it works even after a fork bomb fills the pid limit. Shell commands raise their own OOM score so that running out of memory kills the command, not PID 1.
- **Everything the host reads from a container is capped at the source:**
  - shell output, through `head -c` inside the container, to 64 KB; the command then dies of SIGPIPE (`shell.stopped`);
  - the workspace listing, to 200 entries plus a count;
  - file reads.
- **Weekly copy** (`workspace_sync`): files are enumerated with `find -type f` and checked by apparent size and count before anything is copied (50 MB total, 5,000 files, 5 MB per file). Skips are logged, and only regular files are copied, with no tar.
- **Symlinks:** the host never follows agent-made ones. The `files` tool runs inside the container, and the no-sandbox `tools.Workspace` opens paths component by component with `O_NOFOLLOW`. Keep it that way: anything in the workspace or a repo is agent-controlled.
- **After changing any of this**, run `uv run python -m orchestrator.sandbox check`. It should report 20/20, covering reachability, egress through Gitea (migrate, mirror, push mirror, webhook to a reachable host) and tenancy (agent B vs agent A).

## Conventions

- **The referee sees only public facts**: `referee.PUBLIC_FIELDS` plus `starting_state.network` (no goal, no traits, no agent conversation), and for `apply` with a `repo` or for `launch`, the repo as a visitor would see it on Gitea (description, file list, README, commit count). Keep it that way. Sensitivity runs change one trait and must not leak it into outcomes directly.
- **The agent never sees `horizon`, `base_rate`, or `reply_rate`.** The opening order is shuffled per run (`world.shuffled`, logged as `run_start.opening_order`) so list position can't masquerade as preference. The catalog is in the week prompt, not the system prompt: openings the agent can't apply to (accepted, waiting to hear back, or before the reapply week) are left out, with a one-line count; `week_start.openings_hidden` / `openings_hidden_ids` log them with the reason. Persona YAML is re-dumped with yaml, so comments in the file never reach the model.
- **Referee determinism:** the referee is a probability estimator at `temperature=0, seed=0` on Ollama, so the same application always gets the same odds, and replaying `referee_decision.referee_input` reproduces `raw_output` exactly. All outcome variance comes from the keyed dice. Current Claude models reject sampling parameters, so Anthropic referee estimates are *not* deterministic; the log then records `temperature: null`.
- **Calibration:** `estimated_chance` vs `base_rate` measures the referee's bias. Realized vs estimated only checks the dice; it matches in expectation by construction.
- **Every number in openings.yaml is illustrative** (`illustrative: true` at the top, required by `world.load_world`, logged as `run_start.world_illustrative`): base and reply rates, pay, amounts, time costs, the gig, the forum. Don't cite results as grounded until they're sourced (question 3).
- **Prompt and world wording are part of the experiment.** Any change to `SYSTEM`, the week prompt, the referee or reflection prompts, the time rules, or openings.yaml changes results. Note it in the commit message and don't compare runs across such changes.
- **Every event goes in the JSONL log**: one line per event, with `ts`, `run_id`, `week`, `type`. Types: `run_start` (full config, system prompt, tools), `week_start` (state, news, broke, carried errors, openings hidden, full week prompt), `llm_call` (role, model, usage, latency, running total), `agent_text`, `nudge`, `tool_call` (input, output truncated to 4000 chars), `tool_error` (tool, full input, error), `tool_errors_carried`, `referee_decision` (full referee input + raw output, estimate, base/reply rate, run seed, success/reply draws, outcome, referee temperature/seed), `outcome_applied`, `outcome_expired`, `commitment_started`, `commitment_ended` (reason term/left), `offer_held`, `offer_lapsed`, `broke`, `gig`, `week_end` (reason, actions, used, valid, invalid, shortfall, digest, key events, state), `memory_reflection`, `shell` (command, exit code, timed out, stopped, output ≤ 64 KB), `launch` (repo snapshot, title, pitch, full referee input + raw output, estimate, base rate, draw, outcome, upvotes), `repo_created`, `sandbox_started` (container, network, user), `workspace_sync` (copied, bytes, skipped with reasons), `workspace_sync_failed`, `sandbox_stopped`, `repos_exported`, `gitea_user_deleted`, `sandbox_teardown_failed`, `referee_baseline_start` / `referee_baseline` / `referee_baseline_summary` (in the batch's baseline file), `agent_thinking` (summarized thinking per agent call), `idea` (from `wait`; a measurement, never fed back into prompts), `closing_turn`, `message` (contact, text, dice key/draw, replied, reply, offer, offer_problem, full contact input + raw output), `contact_offer`, `spend` (item, price, contractor or ad, company balance), `api_error`, `run_end` (reason: horizon / token_budget / api_error / error / interrupted, weeks, models, tokens, `cost_usd`, launches, repos, valid/invalid actions, `valid_action_rate`, final state). `run_start` also has `seed`, `order_seed`, `dice_seed`, `opening_order`, `code`, `sandbox`, `world_illustrative`, `sources`; `referee_decision` also has `position` and `repo`; `llm_call` also has `cost_usd`, `raw_usage`, `served_model`. When you add behavior, add a log event; analysis depends on logs alone.
- **API failures are not world events.** Any model call that fails for good raises `backends.APIError`: a spend limit (classified as `kind: "spend_limit"`), auth, any 4xx, a 5xx or connection error after retries (Anthropic SDK `MAX_RETRIES` = 4; Ollama 3 attempts). `Run._call` logs `api_error` (role, status, kind, message, request id) and the run ends with `run_end.reason = "api_error"`. The interrupted week never reaches `week_end`, so its actions aren't counted, and nothing about it reaches the agent, the referee, or the track record. The batch then stops (later runs would hit the same limit). A failure during the referee baseline starts no runs. Never catch `APIError` as a `ToolError`.
- Tool argument errors come from `tools.validate` and must say what was wrong and what was expected; the agent sees them as tool results, or in next week's "Problems last week" if the week ended first.
- Money is in dollars. `weekly_expenses` defaults to $1,000 (a persona can override it), and starting cash is `savings_weeks × weekly_expenses`. Company investment is tracked separately (`company_funding`) and does not pay living expenses.
- Tool schemas are written once in Anthropic shape in `tools.py`. `OllamaConversation` converts them.
- Anthropic backend: thinking is always on for current models, so `max_tokens` is 16000 and `effort` is set explicitly (`backends.EFFORT`). The agent's conversation asks for `thinking.display = "summarized"` so summaries can be logged; it doesn't change how much the model thinks or what's billed. Models in `FALLBACK_MODELS` use the beta endpoint with `fallbacks="default"`. Don't use forced `tool_choice` (it returns 400 on current models).
- Ollama backend: sends `reasoning_effort: "none"`. That is the only switch that turns qwen3 thinking off through the OpenAI-compatible endpoint (`/no_think` in a prompt does not); it takes calls from ~25s to ~1s.
- Python 3.12, uv, no package build (`[tool.uv] package = false`). Run modules with `uv run python -m orchestrator.<name>`. HTTP uses `httpx2` (what `anthropic` 2.x uses), not `httpx`.
